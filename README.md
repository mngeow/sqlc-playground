# sqlc-playground

A small Go and SQLite learning project showing how **[sqlc](https://sqlc.dev/)**
works with **[Goose](https://github.com/pressly/goose)**:

- **Goose** applies versioned SQL migrations to a database.
- **sqlc** reads the schema and SQL queries and generates type-safe Go code.
- **Go** calls the generated methods through `database/sql`, using the
  `modernc.org/sqlite` driver.

The example creates authors and books, links books to their authors with a foreign
key, and demonstrates inserts and reads using generated Go methods.

## How the pieces fit together

```text
migrations/ --------------------> Goose ----------> playground.db
     |
     +---- schema input ----+
                            |
queries/ ---- query input ---+---> sqlc -----------> tutorial/
                                                       |
                                                       v
                                                   main.go
                                                       |
                                                       v
                                                  playground.db
```

The migration files are shared inputs: Goose executes them against SQLite, while
sqlc uses their schema definitions to understand tables and column types. sqlc
recognizes Goose's migration annotations and ignores the rollback SQL when
building its schema model.

**`goose up` changes the database; `sqlc generate` changes the generated Go code.**
Run both after a schema change. A query-only change needs `sqlc generate`.

## Quick start

### 1. Install the tools

You need Git and Go (the version specified in [`go.mod`](go.mod) or newer). SQLite
runs locally through the Go driver; no database server is required.

Install the CLI versions used by this project:

```powershell
go install github.com/sqlc-dev/sqlc/cmd/sqlc@v1.31.1
go install github.com/pressly/goose/v3/cmd/goose@v3.28.0
```

Ensure Go's binary directory (normally `$HOME\go\bin` on Windows) is on your `PATH`.

### 2. Clone and configure

The examples use PowerShell. Clone the repository using a GitHub account with
access to it:

```powershell
git clone https://github.com/mngeow/sqlc-playground.git
Set-Location sqlc-playground
go mod download
Copy-Item .env.example .env
```

Run all subsequent commands from the **project root** so the relative paths and
Goose's automatic `.env` loading work as expected.

### 3. Migrate, generate, and run

```powershell
goose up
goose status
sqlc generate
go run .
```

The first `goose up` creates `playground.db` and applies the `authors` and `books`
migrations in order. Goose records the applied versions in `goose_db_version`, so
subsequent runs apply only pending migrations.

The demo in `main.go`:

1. Lists the existing authors (empty on a fresh database).
2. Creates an author named Brian Kernighan.
3. Fetches that author and prints `true` when the inserted and fetched values match.
4. Creates a book named Go Programming 101 linked to that author.

Each run adds another author and book to the file-backed database.

### `migrations/`: evolve the database schema

Add tables, columns, constraints, and indexes here. Goose uses numeric filename
prefixes to determine migration order. Each SQL migration has an `Up` section and,
in this project, a corresponding `Down` section:

```sql
-- +goose Up
CREATE TABLE authors (
  id INTEGER PRIMARY KEY,
  name text NOT NULL,
  bio text
);

-- +goose Down
DROP TABLE authors;
```

Create a new numbered migration for a schema change:

```powershell
goose -s create add_book_isbn sql
```

Use new migration files for changes to an already-applied schema: Goose tracks
versions and does not rerun a migration just because its contents changed.

### `queries/`: write the SQL your application will call

Each query starts with a sqlc annotation, for example:

```sql
-- name: CreateAuthor :one
INSERT INTO authors (name, bio)
VALUES (?, ?)
RETURNING *;
```

`CreateAuthor` becomes a Go method. The `?` placeholders become method parameters,
and `RETURNING *` returns the saved row, including its generated ID.

| Annotation | Generated method behavior | Existing example |
| --- | --- | --- |
| `:one` | Returns one result and an error | `CreateAuthor`, `GetBook` |
| `:many` | Returns a slice of results and an error | `ListAuthors` |
| `:exec` | Executes SQL and returns an error | `UpdateAuthor`, `DeleteAuthor` |

Edit or add queries in these files, then run `sqlc generate`.

### `tutorial/`: inspect the generated Go API

Read this folder to see how SQL becomes Go methods, parameter structs, and model
types. Make changes through `queries/`, `migrations/`, or `sqlc.yaml` and regenerate;
manual edits to generated files will be overwritten.

sqlc uses column nullability to choose Go types:

| Column | SQL definition | Generated Go type |
| --- | --- | --- |
| `authors.name`, `books.name` | `text NOT NULL` | `string` |
| `authors.bio` | `text` | `sql.NullString` |
| `books.author_id` | `INTEGER REFERENCES authors(id)` | `sql.NullInt64` |

A foreign key can still be nullable. After fetching an author, `main.go` supplies
the book parameters like this:

```go
insertedBook, err := queries.CreateBook(ctx, tutorial.CreateBookParams{
    Name:     "Go Programming 101",
    AuthorID: sql.NullInt64{Int64: fetchedAuthor.ID, Valid: true},
})
if err != nil {
    return err
}
log.Println(insertedBook)
```

`Valid: true` stores the supplied value; `Valid: false` stores SQL `NULL`.

### `main.go`: experiment with the generated methods

This is the application entry point. It opens SQLite, creates a query helper with
`tutorial.New(db)`, and calls the generated methods. Add calls here as you learn,
then run `go run .` from the project root.

The application connects to the database through this line:

```go
db, err := sql.Open("sqlite", "./playground.db?_pragma=foreign_keys(1)")
```

### `cmd/createdb/`: create a separate practice database

This standalone command creates an initialized, empty SQLite file:

```powershell
go run ./cmd/createdb -db ./practice.db
```

The `-db` flag defaults to `./new.db`. The parent directory must exist, and the
command returns an error if the file already exists.

Apply the schema to the new file with:

```powershell
goose -env=none -dir ./migrations sqlite3 "./practice.db?_pragma=foreign_keys(1)" up
```

`-env=none` disables loading the default settings from `.env` for this command.
To use this file with the demo, also change the connection string in `main.go`
to `./practice.db?_pragma=foreign_keys(1)`.

## Configuration

### Goose: `.env` and `.env.example`

Goose automatically loads `.env` from the current directory:

```dotenv
GOOSE_DRIVER=sqlite3
GOOSE_DBSTRING="./playground.db?_pragma=foreign_keys(1)"
GOOSE_MIGRATION_DIR=./migrations
```

- `GOOSE_DRIVER` selects Goose's SQLite driver, named `sqlite3`.
- `GOOSE_DBSTRING` selects the local database file and connection options.
- `GOOSE_MIGRATION_DIR` selects the directory containing the migration files.

`_pragma=foreign_keys(1)` enables foreign-key enforcement on each connection opened
through that connection string. The Go application uses the same option with its
driver name, `sqlite`.

**Only Goose loads `.env` automatically in this project.** When changing the
database used by the project, update both `GOOSE_DBSTRING` in `.env` and the
connection string in `main.go` to point at the same file.

The local `.env`, root-level `*.db` files, and their SQLite sidecar files are
git-ignored. `.env.example` is the tracked template for new checkouts.

### sqlc: `sqlc.yaml`

```yaml
version: "2"
sql:
  - engine: "sqlite"
    queries: "queries"
    schema: "migrations"
    gen:
      go:
        package: "tutorial"
        out: "tutorial"
```

- `engine` selects sqlc's SQL dialect.
- `queries` points to the SQL query files.
- `schema` points to the migration files that define the schema.
- `gen.go.package` sets the generated Go package name.
- `gen.go.out` sets the generated code's output folder.

If you move `migrations/`, update both `schema` here and `GOOSE_MIGRATION_DIR` in
`.env`. If you move `queries/`, update `queries`. If you change the generated
package or output folder, update the corresponding import and references in
`main.go`, then regenerate.

sqlc reads these files to generate code; it does not need to connect to the local
SQLite database for this configuration.

## Hands-on learning exercises

### 1. Add a query

Append this query to `queries/books.sql`:

```sql
-- name: ListBooksByAuthor :many
SELECT * FROM books
WHERE author_id = ?
ORDER BY name;
```

Run `sqlc generate`, then inspect `tutorial/books.sql.go` for the generated
`ListBooksByAuthor` method and its parameter type. Call it in `main.go` after
creating a book, handle its error, and print the returned slice. This exercise
uses the existing schema, so it only needs code generation.

### 2. Add a column with a migration

1. Run `goose -s create add_book_isbn sql` (once). With the initial two migrations,
   this creates `migrations/00003_add_book_isbn.sql`.
2. Give the new migration these contents:

   ```sql
   -- +goose Up
   ALTER TABLE books ADD COLUMN isbn text;

   -- +goose Down
   ALTER TABLE books DROP COLUMN isbn;
   ```

3. Update the existing `CreateBook` query in `queries/books.sql` to accept ISBN:

   ```sql
   -- name: CreateBook :one
   INSERT INTO books (name, author_id, isbn)
   VALUES (?, ?, ?)
   RETURNING *;
   ```

4. Run `goose up` to update the database, then `sqlc generate` to update the Go API.
5. Inspect `tutorial/models.go` and `tutorial/books.sql.go` for the new nullable
   string field. Supply it in `main.go` using
   `sql.NullString{String: "example-isbn", Valid: true}`.
6. Run `go run .` and inspect the inserted book in the output.

This is the core workflow: **change schema -> migrate -> change queries -> generate
Go code -> update application calls -> run**.

### 3. Explore rollback behavior

```powershell
goose status
goose down
goose status
goose up
```

`goose down` executes the latest applied migration's `Down` section. With the
initial migrations it drops `books` and its rows; after the ISBN exercise it drops
the `isbn` column and its values. Applying the migration again restores the schema,
but not the removed data.

Rollback affects the database, while sqlc still reads all migration files' `Up`
sections. Return the database to the latest version with `goose up` before running
the latest generated code.

## Useful commands

| Command | Purpose |
| --- | --- |
| `goose up` | Apply pending database migrations |
| `goose status` | Show applied and pending migrations |
| `goose version` | Show the current database schema version |
| `goose down` | Roll back the latest applied migration |
| `goose validate` | Check migration file structure without executing SQL |
| `sqlc compile` | Check schema and queries without generating Go files |
| `sqlc generate` | Generate Go code from the schema and queries |
| `go build ./...` | Compile all Go packages |
| `go run .` | Run the author/book example |

If you see `no such table`, run `goose up` and check that Goose and `main.go` point
to the same database. For incompatible Go parameter types, inspect the generated
parameter struct and the source column's nullability, then regenerate after any
SQL changes.
